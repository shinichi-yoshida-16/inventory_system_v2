# 要件定義
## 1. 背景・目的
- 要件定義からテストまで、AIを利用して対応する体制をとる。
- 中古自動車販売の整備工場における、部品・消耗品の在庫管理を行うシステムを開発する。現状は紙ベースでの管理と想定し、以下の課題解消を目的に、システムの新規開発を行う。
  - 在庫管理が手作業かつリアルタイムの把握ができない
  - 入庫・出庫管理ができていない
  - 欠品に気が付けない

## 2. システム概要
- システム名称
  - 整備部品在庫管理システムv2
- 想定ユーザ
  - 整備士(10名程度)
  - 管理者級の整備士を置き、上記10名のうち2名程度とする
  - 管理者級の整備士は、管理者権限画面の操作ができる
- 認証方式
  - Nuxtjsにより実装、パスワードはbcryptjsでの暗号化を行う
  - Nuxtjsの状態管理機能によりセッション管理を行う
- ユーザ操作端末
  - 個人所有のスマートフォン
    - QR読み取り、在庫確認
  - 貸与PC
    - QRコード発行と印刷、閾値設定、在庫の手動操作
- 管理対象
  - 部品・消耗品などの在庫
- 開発方針
  - Googleサービスを中心としたローコスト構成をとる
  - DBはGoogleスプレッドシートを軸に検討
- 出口
  - 検証可能な程度の完成度

## 3. 業務フロー
### 3-1. ユーザ登録
1. 利用者にメールアドレスおよびパスワードを確認する
2. パスワードは、CLIツール（`npm run hash-password`）に手入力してbcryptハッシュを生成する
3. Googleスプレッドシートの許可リストに、メールアドレスと生成したハッシュを含む必要情報を記載する

### 3-2. ログイン
1. webブラウザでログイン画面を開く
2. あらかじめ登録済みのメールアドレスとパスワードを入力する
3. ログインボタンを押下する
4. ログイン認証が出来ればダッシュボード画面に遷移する
5. ログイン不正であれば、エラーメッセージが表示されログイン画面にとどまる

### 3-3. セッション管理
1. ログイン認証後、セッションIDとセッション有効期限を設定し、状態管理機能によって保持する
2. セッション有効期限は、ユーザ操作毎に更新する
3. セッション有効期限が切れたセッションは自動で消去し、ログイン画面に強制遷移する
4. ログアウトボタンをクリック後、セッションは消去する

### 3-4. 在庫リスト確認
1. ログイン処理を行う
2. 在庫一覧ボタンをクリックする
3. 在庫一覧画面が表示される

### 3-5. 新規在庫登録
1. スマートフォンにて、ログイン処理を行う
2. QR読み取り画面を表示する
3. カメラを起動する
4. バーコードを読み取り、バーコード情報が表示されるまで待機する
5. 入庫する商品情報を入力し、在庫登録を行う
6. 正常に在庫登録されたことを確認する
7. 在庫登録に失敗した場合はエラーを表示し、再実行を促す（新規登録は排他ロックを取得できなければ即時エラーとし、時差更新の対象外とする）

### 3-6. 入庫処理
1. スマートフォンにて、ログイン処理を行う
2. QR読み取り画面を表示する
3. カメラを起動する
4. バーコードを読み取り、バーコード情報が表示されるまで待機する
5. 入庫ボタンをクリックする
6. 正常に入庫登録されたことを確認する
7. 正常に入庫登録されなかった場合、時差更新となる

### 3-7. 出庫処理
1. スマートフォンにて、ログイン処理を行う
2. QR読み取り画面を表示する
3. カメラを起動する
4. バーコードを読み取り、バーコード情報が表示されるまで待機する
5. 出庫ボタンをクリックする
6. 正常に出庫登録されたことを確認する
7. 正常に出庫登録されなかった場合、時差更新となる

### 3-8. 閾値登録
1. ログイン処理を行う
2. 閾値設定画面を表示する
3. 在庫リストが表示される
4. 閾値入力に閾値を設定し、更新ボタンをクリックする
5. 廃番品目があれば、廃番フラグを設定して更新ボタンをクリックする
6. 正常に閾値登録がされたことを確認する
7. 閾値登録・廃番フラグ更新に失敗した場合はエラーを表示し、再実行を促す（管理者のみ・低競合のため同期リトライのみとし、時差更新の対象外とする）

### 3-9. 在庫通知メール
1. 管理者級の整備士が、ユーザ情報画面の通知先設定にメールアドレスを登録する
2. 通知先設定に登録されているメールを対象とする
3. 在庫マスター(7.1)のcurrentStockがthreshold未満になったら、登録されているメールアドレスに対して通知メールを送る
4. 在庫数が補充されて一度thresholdの値以上になるまで、再通知は行わない
5. Gmailの送信数上限に達した場合や送信に失敗した場合は、当日の再送は行わず、マージ対象情報をサーバ（GCS、時差更新の蓄積データと同一バケット）に品目単位で保持する
6. 管理者級整備士のログイン時にマージ対象情報が存在する場合、保留分を1通にまとめてメール通知し、送信成功でマージ対象情報を消去する

### 3-10. ユーザ情報管理
1. ログイン処理を行う
2. ユーザ情報画面に遷移する
3. ログイン中ユーザのパスワード変更ができる
4. 管理者級整備士は、許可リスト(一般ユーザのメールアドレス一覧)の確認と、対象ユーザのパスワードのリセット(再設定)ができる（ユーザの追加・削除はDBの直接編集）
5. 管理者級整備士は、通知先設定(在庫アラートメールの送信先メールアドレス)の追加・削除ができる(3-9)

### 3-11. 操作ログ
1. 入庫・出荷処理を行うごとに、どの在庫を、誰が、いつ、どれだけ入庫/出庫したかをTransactionLogに記録する

### 3-12. 時差更新
1. DB更新処理の失敗による時差更新用データが存在する時、在庫一覧画面の時差更新ボタンが活性化する（管理者権限ユーザのみ表示）
2. 管理者級整備士が、時差更新ボタンを押下する
3. 蓄積データによる、時差更新を行う
4. 更新が正常に完了できなかった場合、蓄積データを保持して再度の時差更新をユーザに促す
5. 更新が正常に完了できた場合、蓄積データを消去して更新完了をユーザに通知する

## 4. 機能要件
- FR-01
  - ログイン機能
    - メールアドレスとパスワードを入力し、AllowListと照合する
    - 一致した場合のみダッシュボードに遷移し、以降の操作者情報として保持する
    - 未登録メールアドレス、パスワード不一致または退職フラグがtrueの場合はアクセスを拒否する
- FR-02
  - 在庫一覧表示UI
    - 品目ID、品目、現在在庫数、アラート閾値を一覧表示
    - 管理者級の整備士はデータベースの直接編集が可能
- FR-03
  - QRコード生成機能
    - 品目ID、品目ごとにユニークなQRコードの生成
- FR-04
  - QRコード印刷機能
    - 生成したQRコードをラベル印刷できる形で出力
    - 紙印刷でも可
- FR-05
  - コード読み取り機能(スマホ)
    - スマホのカメラで、自社発行QRコードまたはメーカー添付のバーコード(JANコード/EAN-13、GS1 DataMatrix等)を読み取り、対象品目を特定する
      - ※JANコードは13桁の数字自体がGTIN(先頭に0を付与しGTIN-14として正規化)、GS1 DataMatrixはGS1 Application Identifier構造からAI「01」(GTIN)を抽出し、いずれもGTINとして品目の検索キーに用いる(品目IDそのものではない。品目IDはシステムが自動採番する。7.1参照)。
- FR-06
  - 出庫処理
    - 読み取り後、指定数量を在庫数からマイナスする
    - 出庫後、現在在庫数と閾値を比較して在庫マスターのアラートメール送信済みフラグを更新を判断する
      - マイナス在庫は許容しない。現在在庫数を超える出庫要求は拒否し、在庫マスタ・履歴とも更新しない（在庫マスターへ記録する数量と実際に減算した数量を一致させる）
    - ログイン中のメールアドレスを操作者として入出庫履歴に記録する
- FR-07
  - 入庫処理
    - 読み取り後、指定数量を在庫数にプラスする
    - 入庫後、現在在庫数と閾値を比較して在庫マスターのアラートメール送信済みフラグを更新を判断する
    - ログイン中のメールアドレスを操作者として入出庫履歴に記録する
- FR-08
  - 閾値設定機能
    - 品目ごとにアラート発生の閾値数量を設定
- FR-09
  - 在庫アラートメール自動送信機能
    - 在庫数が閾値を下回った時、通知先設定に登録されているすべてのメールアドレスに自動メール送信
    - アラート送信要否は在庫更新の排他ロック区間内で判定する。実際のメール送信と送信済みフラグの更新はロック解放後に行う独立系とし、送信成功時に在庫マスターのアラートメール送信済みフラグを更新する
    - Gmail送信数上限（HTTP 429）到達時や送信失敗時は、当日中の再送はストップし、マージ対象情報をサーバ（GCS、時差更新の蓄積データと同一バケット）に品目単位で保持する。管理者級整備士のログイン時に、保留分を1通にまとめて送信し、送信成功で送信済みフラグを更新してマージ対象情報を消去する
- FR-10
  - 入出庫履歴記録
    - ログ保存
- FR-11
  - 廃番品目のチェック
    - 廃番(入手不可能な)品目をデータベース上廃番として管理できるようにする
    - 管理者級の整備士のみ操作可能
- FR-12
  - 未登録品目のスキャン時自動登録機能
    - スマホで読み取ったコード(GTIN)が在庫マスタに未登録の場合、その場で品目名・アラート閾値・保管場所を入力して新規登録できる
    - 品目IDはシステムが自動採番(ITM-000123形式)し、読み取ったGTINは別項目として在庫マスタに保持する(7.1)
    - 登録と同時に、読み取った1点を入庫として記録する(在庫数0のままでの登録は行わない)
    - 新規登録直後は入庫(IN)のみ可能とし、出庫はできない(未登録品目からの出庫は不整合となるため)
- FR-13
  - ユーザ情報更新
    - ログイン中ユーザのパスワード更新ができる
- FR-14
  - 排他制御
    - 入庫/出庫について、ユーザ同士のDB更新タイミングが重なってしまった場合、先の更新処理が終わるまで次の更新処理を待機する
      - 更新タイミングの重複は、排他ロックが取得できたか否かで判断する
        - 排他ロックを取得できなかった場合、先処理の更新待ちをする
        - 待ち時間が長い場合、時差更新として一旦ユーザに通知を行い更新処理を閉じて画面に操作を返す
          - 待ち時間は、5-10s程度で検討する
        - 一時データ(蓄積データ)はGoogleStorageバケット上で、jsonファイルとして保持する
          - 保持可能性は6.2にて検証済み(technical_verification.md「検証1」。GCSでの保持は可能。バケット作成とSA権限付与が実装前提)
          - 排他ロックはスプレッドシート単体では取得できないため、GCSオブジェクトの`ifGenerationMatch=0`によるロックで実現する(technical_verification.md「検証2」)
- FR-15
  - 時差更新
    - 対象は入庫・出庫処理とする。新規品目登録・閾値設定・廃番フラグ更新は時差更新の対象外（同期リトライのみ）
    - 何らかの原因(排他制御等)で、Googleスプレッドシートの入出庫更新ができなかった場合、サーバ上に一時データを時系列順に残しておき、後追いでGoogleスプレッドシートの更新を行う
    - 時差更新は、管理者権限ユーザが専用のボタンを押下して行う
      - 時差更新実施時、更新できなければユーザにその旨を通知して、再度の実施を促す
      - 最悪、棚卸でDB更新を行う運用とする

## 5. 非機能要件
- NR-01
  - 利用者数
    - 最大アクセス数は最大10名(在籍している整備士の人数)程度
- NR-02
  - 可用性
    - 致命的な業務停止を避ける代替手段を用意
    - 最悪、復旧後に棚卸等行う運用
- NR-03
  - セキュリティ
    - 利用者は整備士に限定
    - 登録されたメールアドレス+パスワードによる認証を行う
- NR-04
  - コスト
    - 原則、Googleサービスの無料枠の範囲で運用する
    - Gmail送信数の日次上限に留意する
- NR-05
  - 保守性
  - 一人開発+AIコード生成を前提に、コードコメント・処理の単純化を重視し、属人化を避ける設計とする
- NR-06
  - 拡張性
  - 将来的な品目数増加、拠点追加、他システム連携を見据えた最低限の拡張余地を残す

- QRコード生成・印刷
  - JS製QRコード生成ライブラリを利用した内製

技術検証を 2026-09-08 に実施。詳細および検証コードの所在は [technical_verification.md](technical_verification.md) を参照。検証項目・結果・関連要件のトレースは以下のとおり。

| # | 検証項目 | 結果 | 関連要件 | 詳細 |
|---|---|---|---|---|
| 1 | GoogleCloud上に、更新失敗時の一時データ(蓄積データ)を保持できるか | **可能**。GCSバケットにJSONオブジェクトとして保持(Cloud Run→GCSの標準構成)。バケット作成とCloud Run実行SAへの権限付与が前提 | FR-14, FR-15 | technical_verification.md「検証1」 |

| 3 | GoogleCloudで、Gmailの送信数制限はあるか | **あり**(無料Gmail 500通/日、Workspace 2,000通/日。引き上げ不可)。業務規模では上限に十分収まる。送信認証方式の準備(SA単体では送信不可)が課題 | FR-09, NR-04 | technical_verification.md「検証3」 |

## 7. データ設計
### 7.1. 在庫マスター(InventoryMaster)
品目ID: 一意の識別子。登録経路によらずシステムが自動採番する`ITM-000123`形式(6桁連番)
GTIN: 任意。メーカー添付バーコードから登録した場合に、正規化済みGTIN-14(JANコードは13桁+先頭0でGTIN-14化、GS1 DataMatrixはAI「01」から抽出した値)を保持する。読み取り時の品目検索キーとして使う(品目IDそのものではない)
品目名
現在在庫数
閾値: アラートメールの発生ライン
アラート送信済みフラグ: アラートメール送信でtrue、閾値以上に入庫されたときtrueならばfalseにする
保管場所: 任意
廃番フラグ: 廃番時にtrue、画面で設定
更新年月日

### 7.2. 入出庫履歴(TransactionLog)
入出庫日時
品目ID
種別:入庫 or 出庫
数量
ユーザ識別: メールアドレスを操作者として取得

### 7.3. 通知先設定(NotificationTargets)
#### ※品目ごとの紐付けは行わず、登録済み全アドレスへ一律通知する
通知先ID
通知先メールアドレス
更新年月日

### 7.4. 許可リスト(AllowList)
許可ID
許可メールアドレス
パスワード : bcryptによる暗号化済み文字列
通知先ID: 管理者であれば通知先設定にメールアドレスを追加、非管理者であれば空白
退職フラグ
更新年月日

## 10. リスクとその対応方針
- 通信失敗
  - プログラム的にリトライを行う
- 退職・異動時のアクセス権限失効漏れ
  - 許可リストの定期棚卸を行う
- なりすましリスク
  - 検証レベルの運用として許容する
- 管理者のDB直接編集との競合リスク
  - 管理者のスプレッドシート直接編集は、排他制御の対象外とする
  - 対応:整備作業中(整備士がQRスキャンで入出庫操作を行っている時間帯)は直接編集を行わない運用ルールとし、技術的な排他制御は行わない。万一競合が発生した場合は、定期棚卸(NR-02と同様の運用)で在庫数を実数に合わせて解消する
- 識別コード形式追加(JAN/GS1 DataMatrix)によるコード解析リスク
  - GS1 DataMatrixはApplication Identifier構造の解析が必要で、対応する識別子(AI)を網羅していない場合、GTINを正しく抽出できない可能性がある
  - 対応: 主要なAI(GTIN=01等)のみに対応する簡易パーサとし、未対応AIや解析失敗時はエラーとして扱い、誤った値をitemIdとして登録しない設計とする。簡易パーサでのAI01抽出・未対応AIのエラー化は技術検証で実証済み(technical_verification.md「検証4」)。実機での読み取り検証は`verification/`(git管理外)で継続する
- GoogleCloudから特定のメールアドレスにGmail送信が可能かの技術的検証
  - 6.2 にて検証済み(technical_verification.md「検証3」)。送信数上限は業務規模では問題なし。ただしサービスアカウント単体ではGmail送信不可のため、通知専用Gmail + OAuth2リフレッシュトークン方式を軸に、設計フェーズで送信認証方式を確定する
- JANコードとQRコードの管理の混在
  - 運用でカバーしてもらうが、基本JANコードを用いて管理する
